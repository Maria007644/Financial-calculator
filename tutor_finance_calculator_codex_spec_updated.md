# Техническое задание для Codex: финансовый калькулятор репетитора с геймификацией

## 0. Роль Codex и общий результат

Создай полностью рабочий **одностраничный веб-сайт / web app финансового калькулятора для частного репетитора**.

Приложение должно помогать преподавателю ответить на четыре вопроса за несколько секунд:

1. **Сколько я заработаю сегодня / на этой неделе / в этом месяце?**
2. **Сколько денег мне нужно заработать за выбранный период?**
3. **Хватает ли моего текущего расписания, чтобы достичь финансовой цели с учетом расходов?**
4. **Что изменится, если я добавлю / уберу урок или поменяю цену?**

Главный принцип продукта: **не бухгалтерия, а приятный визуальный финансовый планер для репетитора**.

Сайт должен ощущаться легким, теплым, современным, живым и мотивирующим. Интерфейс не должен выглядеть как банковское приложение, Excel или корпоративная CRM.

**ВАЖНО:** в проекте есть файл `reference.png`. Перед созданием финального UI обязательно изучить его и строить визуальную систему максимально близко к нему по композиции, палитре, глубине, карточкам, теням, размерам и общему характеру. Все художественные PNG уже лежат в папке `Assets` и перечислены далее в этом ТЗ.

# 1. Важные ограничения проекта

## 1.1. Хранение данных

Все пользовательские данные хранить **только в браузере через `localStorage`**.

Backend, Firebase, Supabase, регистрация и авторизация для первой версии НЕ нужны.

Использовать versioned storage key, например:

```text
tutorFinanceApp:v1
```

Все данные хранить в одном корневом объекте JSON либо в небольшом количестве четко именованных ключей.

Обязательно:

- безопасно обрабатывать отсутствие данных;
- безопасно обрабатывать поврежденный JSON;
- иметь `schemaVersion`;
- предусмотреть миграции структуры данных между будущими версиями;
- использовать `localStorage.getItem()` / `setItem()`, а не обращаться к ключам как к свойствам объекта;
- все изменения интерфейса сначала обновляют state приложения, затем выполняют единый save;
- не выполнять десятки записей в localStorage на каждый пиксель drag/animation;
- debounce сохранения при частом редактировании;
- не хранить изображения в base64 в localStorage;
- ассеты хранить обычными файлами проекта.

### Важно о надежности

Так как localStorage привязан к браузеру / origin и пользователь может очистить данные браузера, обязательно реализовать:

- **Экспорт данных в JSON**;
- **Импорт данных из JSON**;
- кнопку **«Создать резервную копию»**;
- кнопку **«Восстановить из файла»**;
- подтверждение перед полной очисткой данных.

Это важная часть продукта, а не необязательная мелочь.

Поля:

- сколько хочу заработать;
- период цели.

Варианты периода:

- месяц;
- год;
- произвольный диапазон дат.

По умолчанию предложить **текущий месяц**.

Пример:

```text

120 000 ₽
```

## Шаг 2. Стоимость занятий

Пользователь вводит базовые цены:

- Индивидуальное занятие — цена за урок;
- Парное занятие — цена за ученика ИЛИ за урок;
- Групповое занятие — цена за ученика ИЛИ за группу.

- техника — 24 000 ₽ / год;

```text

```

Предложить добавить первый регулярный урок.

После завершения показать небольшую celebratory animation и открыть Dashboard.

# 6. Финансовая цель

Создать отдельный удобный блок **«Моя цель»**.

Пользователь всегда может нажать на сумму и отредактировать ее.

Поля цели:

```ts
Goal {
  id: string
  title: string
  targetAmount: number
  periodType: 'month' | 'year' | 'custom'
  startDate: string
  endDate: string
  createdAt: string
  updatedAt: string
}
```

В первой версии активна одна основная цель, но структуру данных сделать так, чтобы позже можно было поддержать историю целей.

### На карточке цели показывать

- цель;
- прогнозный доход за период;
- чистый прогноз после расходов;
- процент достижения;
- сколько не хватает / насколько цель превышена;
- progress bar;
- milestone markers: 25%, 50%, 75%, 100%.

### Формула прогресса

Основной прогресс считать по **чистому прогнозному доходу**:

```text
netForecast = forecastIncome - allocatedExpenses
progress = netForecast / targetAmount
```

Но рядом дать маленький переключатель или tooltip:

```text
Считать цель по:
• чистому доходу
○ выручке
```

Настройку сохранять.

### Если цель достигнута

Не останавливать progress bar визуально жестко на 100%.

Можно показывать:

```text
Цель выполнена на 112%
+14 400 ₽ сверх цели
```

Сам bar можно заполнить до 100%, а превышение показать отдельной glowing pill.

# 9. Формула дохода одного занятия

Функция должна быть централизована и покрыта тестами.

Псевдологика:

```ts
function calculateLessonRevenue(lesson, pricing) {
  if (lesson.customPrice != null) {
    return lesson.customPricingMode === 'perStudent'
      ? lesson.customPrice * lesson.studentCount
      : lesson.customPrice;
  }

  const rule = pricing[lesson.type];

  if (rule.mode === 'perStudent') {
    return rule.amount * lesson.studentCount;
  }

  return rule.amount;
}
```

### Индивидуальное

Всегда studentCount = 1.

### Парное

По умолчанию studentCount = 2.

### Группа

studentCount пользователь вводит сам.

# 10. Расчет дохода за день, неделю и месяц

Это одна из самых важных частей приложения.

## 10.1. День

```text
Доход дня = сумма дохода всех занятий выбранной даты
```

## 10.2. Неделя

```text
Доход недели = сумма дохода занятий с понедельника по воскресенье
```

## 10.3. Месяц

НЕ использовать грубое:

```text
weeklyIncome * 4
```

и НЕ использовать всегда `* 4.33` как основной точный прогноз.

Нужно генерировать occurrences recurring lessons по **реальному календарю выбранного месяца**.

То есть если в месяце 5 понедельников — понедельничный регулярный урок учитывается 5 раз.

Если 4 вторника — вторничный урок учитывается 4 раза.

### Алгоритм

1. Получить первый и последний день выбранного месяца.
2. Для каждого recurring lesson определить валидные даты в диапазоне.
3. Учитывать `startDate`.
4. Учитывать `endDate`.
5. Учитывать исключенные / отмененные даты.
6. Посчитать revenue каждого occurrence.
7. Суммировать.

Так прогноз будет гораздо полезнее для реального репетитора.

# 11. Фактический и прогнозный доход

Архитектуру сделать с разделением двух понятий:

- **Прогноз** — сколько должно получиться по расписанию;
- **Факт** — сколько реально заработано.

Для MVP можно считать главным именно прогноз.

Но в структуру урока сразу добавить статус:

```ts
status: 'planned' | 'completed' | 'cancelled'
```

И возможность быстро отметить занятие:

- ✅ проведено;
- ✕ отменено.

### Логика

Будущие занятия → прогноз.

Прошедшие completed → факт.

Cancelled → 0, если не включена настройка «оплаченная отмена».

Позже это позволит получить точную аналитику без полной переделки модели.

# 12. Расходы

Нужен отдельный раздел **«Расходы»**.

Главная задача из MVP: пользователь вводит расходы на год, а приложение автоматически распределяет их по месяцам.

Но структура должна быть удобнее одной строки.

## 12.1. Категории расходов

Можно добавлять произвольные расходы.

Каждый expense:

```ts
Expense {
  id: string
  title: string
  amount: number
  frequency: 'annual' | 'monthly' | 'oneTime'
  category: string
  date?: string
  enabled: boolean
}
```

Предустановленные категории:

- обучение;
- сервисы / подписки;
- техника;
- реклама;
- налоги;
- материалы;
- прочее.

Пользователь может создать свою категорию.

## 12.2. Годовая сумма

Если frequency = annual:

```text
monthlyAllocatedExpense = annualAmount / 12
```

UI должен явно объяснять расчет.

Пример:

```text
Canva + сервисы
24 000 ₽ / год
≈ 2 000 ₽ / месяц
```

## 12.3. Месячная сумма

Если frequency = monthly, сумма полностью входит в каждый месяц.

## 12.4. Разовая сумма

Если frequency = oneTime — относится к указанному месяцу.

## 12.5. Итоги

Показывать:

- расходы в год;
- средняя нагрузка в месяц;
- расходы выбранного месяца;
- доход до расходов;
- чистый доход.

# 14. What-if калькулятор

Добавить небольшой блок **«А если…?»**.

Это сильная полезная фича.

Примеры:

- +1 индивидуальный урок в неделю;
- +2 индивидуальных урока в неделю;
- +1 группа в неделю;
- повысить индивидуальную цену на 200 ₽;
- уменьшить количество уроков на 1 в неделю.

Показывать результат:


# 16. Геймификация

Геймификация должна быть **приятной и мотивирующей, но не детской**.

Не использовать бессмысленные игровые механики вроде:

- «зайди 7 дней подряд»;
- случайные монетки за клики;
- leaderboard;
- штрафы;
- потеря streak из-за отсутствия входа.

# 19. Анимации

Пользователь отдельно просит **очень приятные плавные анимации**.

Они должны повышать ощущение качества, но не мешать расчетам.

## 19.1. Общие правила

Использовать transform + opacity там, где возможно.

Не анимировать layout-heavy свойства без необходимости.

Основные duration:

```text
micro interaction: 120–180ms
card / modal: 220–320ms
progress animation: 500–900ms
celebration: до 1200–1800ms, ненавязчиво
```

Easing — мягкий spring-like / cubic-bezier.

## 19.2. Нужные анимации

- card hover: легкий lift;
- button press: subtle scale down;
- page / section transition: fade + translate;
- modal: fade + scale / slide;
- number update: мягкий count-up;
- progress bar: плавное заполнение;
- milestone unlocked: маленький pop;
- asset scene: subtle parallax / floating только для декоративных слоев;
- adding lesson: карточка мягко появляется;
- deleting lesson: collapse + fade;
- changing week: directional slide;
- tooltip: fade;
- success toast: spring entrance.

## 19.3. Reduced motion

Обязательно уважать:

```css
@media (prefers-reduced-motion: reduce)
```

При reduced motion отключить:

- floating loops;
- parallax;
- count-up;
- большие travel animations.

Оставить мгновенные или очень короткие transitions.

# 32. Backup / Import / Export

В Настройках создать блок **«Данные»**.

Кнопки:

```text
[ Скачать резервную копию ]
[ Восстановить из файла ]
[ Очистить все данные ]
```

Экспортировать JSON вида:

```json
{
  "app": "tutor-finance-calculator",
  "exportVersion": 1,
  "exportedAt": "...",
  "data": {}
}
```

При импорте:

1. проверить JSON;
2. проверить app identifier;
3. проверить версию;
4. валидировать минимально необходимую структуру;
5. показать preview / confirmation;
6. только затем заменить текущие данные.

Перед import предложить автоматически скачать backup текущего состояния или хотя бы предупредить о замене.

# 33. Ошибки и валидация

Не позволять:

- отрицательную цену;
- отрицательное количество учеников;
- studentCount = 0 для оплачиваемого урока;
- endDate раньше startDate;
- цель <= 0;
- expense < 0;
- NaN;
- бесконечность;
- невозможные даты.

При удалении recurring lesson показывать confirmation.

При сбросе данных — отдельное серьезное подтверждение.

# 36. Производительность

Приложение небольшое, поэтому не переусложнять оптимизацию.

Но:

- memoize тяжелые selectors при необходимости;
- не пересчитывать весь год на каждый mousemove;
- localStorage synchronous — не делать избыточные записи;
- lazy load тяжелые analytics chunks, если появятся;
- оптимизировать изображения;
- использовать WebP/AVIF там, где подходит;
- не загружать `reference.png` в production UI; он нужен только как визуальный ориентир при разработке;
- загружать декоративные PNG лениво там, где они не above-the-fold;
- hero assets оптимизировать без заметной потери качества.

# 37. Privacy

Так как данные хранятся локально, явно написать в Настройках небольшую спокойную подпись:

```text
Ваши данные хранятся только в этом браузере и не отправляются на сервер.
```

Но не обещать абсолютную безопасность.

Не хранить:

- пароли;
- банковские реквизиты;
- данные карт;
- другую секретную информацию.

Для имен учеников достаточно обычных коротких подписей; приложение не является CRM для хранения чувствительных персональных данных.

# 39. Важный UX-принцип: overview → trend → detail

Главный dashboard отвечает на вопрос «как дела?».

Analytics отвечает «как меняется?».

Schedule / expenses отвечают «из чего получилась цифра?».

Любую агрегированную цифру желательно позволять проследить до ее источников.

Например на карточке «Этот месяц — 96 400 ₽» можно нажать и увидеть:

```text
Индивидуальные: 58 500 ₽
Парные: 14 300 ₽
Группы: 23 600 ₽
```

А затем перейти к соответствующим занятиям.

8. Переключиться на следующий месяц и получить правильный календарный прогноз.

14. Увидеть пересчитанный прогноз.

# 44. Исследовательские выводы, на которых основано ТЗ

При проектировании учитывать следующие найденные практики:

1. Современные приложения для репетиторов объединяют schedule, recurring lessons и income analytics, чтобы расписание становилось источником финансовой картины, а не отдельным календарем.
2. Полезный finance dashboard должен прежде всего быстро отвечать, соответствует ли текущий план цели, а детали должны быть доступны ниже по иерархии.
3. Геймификация в финансовом продукте лучше работает, когда progress bars, milestones и rewards связаны с реальным финансовым результатом, а не просто с частотой открытия приложения.
4. `localStorage` подходит для небольшого local-only MVP и сохраняется между browser sessions, но остается synchronous storage и может быть очищен пользователем; поэтому backup/import/export обязательны для надежности.
5. Данные в localStorage не следует считать секретным защищенным хранилищем. Не хранить банковские и authentication secrets.

# 46. Финальная инструкция Codex

Сначала реализуй **правильную финансовую и календарную механику**, затем UI, затем художественный слой.

Главное качество продукта определяется не количеством функций, а тем, насколько легко пользователь видит связь:

```text
РАСПИСАНИЕ → ДОХОД → РАСХОДЫ → ЧИСТЫЙ ПРОГНОЗ → ЦЕЛЬ
```

Каждое действие пользователя должно сразу отражаться в цифрах.

При добавлении занятия пользователь должен мгновенно понимать, сколько оно добавляет к дню, неделе, месяцу и цели.

При добавлении годовой траты пользователь должен мгновенно видеть ее месячную нагрузку.

При изменении цели интерфейс должен мгновенно обновлять прогресс и smart insight.

`reference.png` и готовая папка `Assets` уже предоставлены. Не менять бизнес-логику без причины: использовать `reference.png` как главный визуальный ориентир, а готовые PNG из `Assets` — как реальные слои hero-сцены, milestone states, sidebar decoration и celebration state. Ничего дополнительно из asset sheet вырезать не нужно.

Финальный результат должен выглядеть как **приятный персональный финансовый планер репетитора, который хочется открывать**, а не как бухгалтерская программа.
